# MODULES.md — کارت دستورالعمل ۵ ماژول اصلی (روی Claude)

> هر ماژول = یک جلسه/چت **تازه** در Claude. برای اجرای هر ماژول:
> ۱) چت جدید باز کن ۲) کارت آن ماژول + سه فایل حافظه + خروجی ماژول قبل را بچسبان ۳) خروجی را بگیر و ذخیره کن.
>
> **سه قانون ضدتداخل (تخطی ممنوع):**
> - هر ماژول فقط **یک ورودی** می‌گیرد و فقط **یک خروجی** می‌دهد.
> - هیچ ماژولی حق تغییر خروجی ماژول دیگر را ندارد — حتی اگر اشکال ببیند، فقط در بخش «هشدارها»ی خروجی خودش گزارش می‌کند.
> - تغییر خروجی‌ها فقط در مرحله Debate انجام می‌شود.

---

## Module A — تحلیل مسئله

**مأموریت:** شکستن مسئله Founder به اجزای کوچک و تعریف ورودی/خروجی هر تسک.
**ورودی:** صورت‌مسئله Founder (+ سه فایل حافظه).
**خروجی (قالب ثابت):**
```
== خروجی ماژول A ==
مسئله در یک جمله: ...
تسک‌ها: T1: (شرح) | ورودی: ... | خروجی: ...
        T2: ...
ابهام‌هایی که فقط Founder می‌تواند رفع کند: ...
هشدارها (خارج از قلمرو من ولی دیدم): ...
```
**ممنوع:** طراحی راه‌حل، انتخاب ابزار، کدنویسی.

**متن شروع جلسه:** «تو ماژول A (تحلیل مسئله) هستی. فقط طبق کارت خودت در MODULES.md عمل کن. ورودی من این است: [صورت‌مسئله]»

---

## Module B — طراحی و معماری

**مأموریت:** طراحی ساختار سیستم و تعیین ارتباط بین اجزا، بر پایه تسک‌های ماژول A.
**ورودی:** خروجی ماژول A.
**خروجی (قالب ثابت):**
```
== خروجی ماژول B ==
معماری پیشنهادی: (اجزا + نمودار متنی جریان داده)
ارتباط اجزا: ...
نیازهای تحقیق برای ماژول C: (سؤال‌های دقیق)
هشدارها: ...
```
**ممنوع:** تغییر تسک‌بندی A، پیاده‌سازی، تحقیق بیرونی.

---

## Module C — تحقیق و داده

**مأموریت:** پاسخ به «نیازهای تحقیق» ماژول B: جمع‌آوری اطلاعات، بررسی منابع، مقایسه گزینه‌ها.
**ورودی:** خروجی ماژول B (+ یافته‌های Gemini اگر Founder گرفته باشد — Gemini لایه تحقیق خارجی است و یافته‌هایش از طریق Founder به این ماژول می‌رسد).
**خروجی (قالب ثابت):**
```
== خروجی ماژول C ==
به ازای هر سؤال تحقیق: جواب + منابع/شواهد + سطح اطمینان N/10 + «معتبر تا: (تاریخ/شرط)»
مقایسه گزینه‌ها: (جدول)
شکاف‌های اطلاعاتی باقی‌مانده: ...
هشدارها: ...
```
**ممنوع:** تغییر معماری B، تصمیم‌گیری بین گزینه‌ها (فقط مقایسه).

---

## Module D — پیاده‌سازی

**مأموریت:** تبدیل طراحی B (با داده‌های C) به کد/محصول اولیه و اجرای اولیه.
**ورودی:** خروجی B + خروجی C (به‌هم‌پیوسته توسط Founder یا ChatGPT).
**خروجی (قالب ثابت):**
```
== خروجی ماژول D ==
نسخه اولیه: (کد/فایل/نتیجه)
دستور اجرا/استفاده: ...
چیزهایی که آگاهانه ساده گرفتم: ...
هشدارها: ...
```
**ممنوع:** تغییر طراحی B (اگر شدنی نبود، در هشدارها بگو و ساده‌ترین تفسیر وفادار را بساز)، تست عمیق (کار E است).

---

## Module E — ارزیابی و تست

**مأموریت:** تست خروجی D، پیدا کردن خطا، پیشنهاد بهینه‌سازی.
**ورودی:** خروجی ماژول D.
**خروجی (قالب ثابت):**
```
== خروجی ماژول E ==
تست‌های انجام‌شده: (چه چیزی، چطور، نتیجه)
خطاها: هر خطا + «ریشه احتمالاً در ماژول: A/B/C/D»
پیشنهادهای بهینه‌سازی: ...
حکم نهایی: قابل‌قبول / نیازمند برگشت به ماژول X
```
**ممنوع:** خود ِتعمیر (فقط گزارش)، تغییر کد D.

---

## حلقه بازخورد محدود (ضد گیرکردن)

اگر حکم E «برگشت به ماژول X» بود: Founder خروجی E را به جلسه‌ای تازه از ماژول X می‌دهد تا فقط بخش معیوب را بازتولید کند، و زنجیره از همان‌جا به پایین تکرار می‌شود.
**حداکثر ۲ دور برگشت.** اگر بعد از ۲ دور حل نشد: توقف کامل ← گزارش به Founder ← تصمیم با اوست (تغییر صورت‌مسئله، تغییر معماری، یا پذیرش محدودیت). این سقف عمداً وجود دارد: نه چرخش بی‌نهایت (انفجار هزینه توکن)، نه رد شدن از خطای ریشه‌ای.
